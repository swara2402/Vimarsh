# VIMARSH Backend

FastAPI serves two deliberately separate surfaces:

1. **Decision API**: the demo-facing, recommendation-only reliability endpoint.
2. **Protected research API**: offline outcome logging, contextual benefit estimation, and constrained batch-allocation recommendations.

Neither surface executes human review or evidence acquisition. The research API is disabled until an operator configures a private token.

## Local setup

From the repository root:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
```

Configure a trusted, locally generated reliability bundle for the decision dashboard:

```bash
export VIMARSH_RELIABILITY_BUNDLE=research/models/reliability/wine_quality_reliability_bundle.joblib
export VIMARSH_CORS_ORIGINS=http://localhost:5173
uvicorn app.main:app --app-dir backend --reload
```

Generate the bundle first by following [the demo-day runbook](../docs/demo-day-runbook.md). The bundle must be generated by the VIMARSH research pipeline. Never accept or load arbitrary user-uploaded joblib artifacts.

## Decision endpoints

- `GET /health`: service health and operating mode.
- `POST /v1/decisions`: transparent baseline recommendation from supplied prediction metadata.
- `GET /v1/reliability/schema`: feature schema from the configured trusted bundle.
- `POST /v1/reliability/decisions`: score a sample with the fitted reliability bundle, then apply the transparent baseline policy.\n- `GET /v1/actions/capabilities`: report which action paths are actually configured.\n- `POST /v1/actions/alternate-model/execute`: explicitly run all non-primary models in the trusted bundle and return their predictions/confidence plus measured inference latency. It accepts no labels and does not automatically replace the primary prediction.

The decision API reports recommendations only. The current serving policy does not invoke the alternate model, route a human review, acquire evidence, or update the research ledger.

## Protected research endpoints

Set a strong server-side token before enabling research routes:

```bash
export VIMARSH_RESEARCH_API_TOKEN='replace-with-a-long-random-secret'
export VIMARSH_OUTCOME_LEDGER=research/data/action_outcomes.jsonl
```

Send the token in the `X-Vimarsh-Research-Token` header. If the token is not configured, research endpoints return HTTP 503. Missing or incorrect tokens receive HTTP 401. Do not place this token in frontend code, commit it, or expose it in browser storage.

- `POST /v1/research/execute/alternate-model`: explicitly run every non-primary model in the trusted local bundle, report each prediction/confidence and measured inference latency, and append a pending outcome record. This is an actual local inference action, not merely a recommendation. It does not estimate monetary/compute cost or choose a winning prediction.
- `GET /v1/research/outcomes/summary`: return aggregate counts after verifying the full ledger. It does not return individual records or labels.
- `POST /v1/research/action-benefit`: estimate context-conditioned action benefit from completed, propensity-logged records.
- `POST /v1/research/allocate`: estimate benefit for each requested case/action pair and pass only positive diagnostic candidates to the constrained allocator.

The allocator enforces one action per case, shared total budget, optional action capacities, and a safe no-allocation fallback. The estimator excludes incomplete or propensity-missing records and abstains when effective sample support is inadequate.

### Example: append a completed outcome

```bash
curl -X POST http://localhost:8000/v1/research/outcomes \
  -H "Content-Type: application/json" \
  -H "X-Vimarsh-Research-Token: $VIMARSH_RESEARCH_API_TOKEN" \
  -d '{
    "case_id":"trial-001",
    "action":"alternate_model",
    "policy_version":"policy-v1",
    "model_version":"primary-v1",
    "baseline_prediction":0,
    "status":"completed",
    "estimated_action_cost":1.0,
    "propensity":0.5,
    "randomized_assignment":true,
    "assignment_id":"randomized-trial-001",
    "context":{"uncertainty":0.4,"harm":1.0},
    "action_result":{"alternate_prediction":1},
    "final_prediction":1,
    "ground_truth":1,
    "observed_cost":0.9,
    "latency_ms":12.0,
    "provider_version":"local-runner-v1"
  }'
```

Only submit a completed record after the outcome and retrospective label are genuinely observed and quality-checked. Do not fabricate propensity, randomization, provider, cost, or latency metadata.

## Ledger and research limitations

- The local JSONL ledger is append-only by application convention and tamper-evident through a SHA-256 hash chain. It is not a distributed database or a substitute for access-controlled backups.
- Concurrent multi-process writers are not coordinated. Use a single API worker for this local ledger; use a transactional database before multi-worker deployment.
- The contextual estimator's lower-bound output is a diagnostic, not a finite-sample guarantee or causal effect estimate.
- Propensity adjustment does not remove unmeasured confounding or repair incorrect logging.
- The dashboard's `/v1/actions/alternate-model/execute` route is an explicit local inference action. It runs only models already present in the trusted local bundle and returns outputs plus measured inference latency; it does not record ground truth or automatically select a final prediction. The protected `/v1/research/execute/alternate-model` route additionally appends a pending event. Submit a separate completed outcome record after a final result and ground truth are genuinely available. Reuse the returned `case_id`, baseline prediction, and `context_for_outcome_completion` values when recording that outcome. Do not invent a propensity. A deterministic/manual run without a defensible assignment propensity is not eligible for the propensity-adjusted estimator.

The allocator recommends allocations; it does not execute selected actions.
- Human review and additional evidence remain non-operational without real providers and measured outcomes.

## Tests

From the repository root:

```bash
PYTHONPATH=backend pytest backend/tests -q
```

The test suite covers API validation, trusted bundle inference, protected research routes, label separation, outcome-ledger writes, contextual estimation, and constrained allocation.
