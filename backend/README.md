# VIMARSH Backend

FastAPI serves three deliberately separate surfaces:

1. **Decision API**: the demo-facing, recommendation-only reliability endpoint.
2. **Local alternate-model inference**: an explicit opt-in route that runs non-primary models from the trusted bundle and reports their outputs and latency.
3. **Protected research API**: offline outcome logging, contextual benefit estimation, and constrained batch-allocation recommendations.

Neither surface executes human review or evidence acquisition. The research API is disabled until an operator configures a private token.

## Local setup

From the repository root:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
```

Configure a trusted, locally generated reliability bundle for the decision dashboard:

```bash
export VIMARSH_RELIABILITY_BUNDLE=research/models/reliability/wine_quality_reliability_bundle.joblib
export VIMARSH_CORS_ORIGINS=http://localhost:5173
uvicorn app.main:app --app-dir backend --reload
```

Generate the bundle first by following [the demo-day runbook](../docs/demo-day-runbook.md). The bundle must be generated by the VIMARSH research pipeline. Never accept or load arbitrary user-uploaded joblib artifacts.

## Decision endpoints

- `GET /health`: service health, `research_preview` mode, and the separate recommendation-only decision mode.
- `POST /v1/decisions`: transparent baseline recommendation from supplied prediction metadata.
- `GET /v1/reliability/schema`: feature schema from the configured trusted bundle.
- `POST /v1/reliability/decisions`: score a sample with the fitted reliability bundle, then apply the transparent baseline policy.
- `GET /v1/actions/capabilities`: report which action paths are actually configured.
- `POST /v1/actions/alternate-model/execute`: explicitly run all non-primary models in the trusted bundle and return their predictions/confidence plus measured inference latency. It accepts no labels and does not automatically replace the primary prediction.

The decision API reports recommendations only. The current serving policy does not invoke the alternate model, route a human review, acquire evidence, or update the research ledger.

## Protected research endpoints

Set a strong server-side token before enabling research routes:

```bash
export VIMARSH_RESEARCH_API_TOKEN='replace-with-a-long-random-secret'
export VIMARSH_OUTCOME_LEDGER=research/data/action_outcomes.jsonl
```

Send the token in the `X-Vimarsh-Research-Token` header. If the token is not configured, research endpoints return HTTP 503. Missing or incorrect tokens receive HTTP 401. Do not place this token in frontend code, commit it, or expose it in browser storage.

- `POST /v1/research/execute/alternate-model`: explicitly run every non-primary model in the trusted local bundle, report each prediction/confidence and measured inference latency, and append a pending outcome record. This is an actual local inference action, not merely a recommendation. It does not estimate monetary/compute cost or choose a winning prediction.
- `POST /v1/research/outcomes/{event_id}/complete`: append a completed child event for an existing pending execution. The original pending event is never edited; duplicate completion is rejected.
- `GET /v1/research/outcomes/summary`: return aggregate counts after verifying the full ledger. It does not return individual records or labels.
- `POST /v1/research/action-benefit`: estimate context-conditioned action benefit from completed, propensity-logged records.
- `POST /v1/research/allocate`: estimate benefit for each requested case/action pair and pass only positive diagnostic candidates to the constrained allocator.

The allocator enforces one action per case, shared total budget, optional action capacities, and a safe no-allocation fallback. The API rejects non-finite numeric inputs, negative/non-finite action costs, negative capacities, duplicate case IDs/actions, and costs for actions not declared available. Feature/context maps and action maps are bounded. The estimator excludes incomplete or propensity-missing records and abstains when effective sample support is inadequate.

### Example: append a completed outcome

```bash
curl -X POST http://localhost:8000/v1/research/outcomes \
  -H "Content-Type: application/json" \
  -H "X-Vimarsh-Research-Token: $VIMARSH_RESEARCH_API_TOKEN" \
  -d '{
    "case_id":"trial-001",
    "action":"alternate_model",
    "policy_version":"policy-v1",
    "model_version":"primary-v1",
    "baseline_prediction":0,
    "status":"completed",
    "estimated_action_cost":1.0,
    "propensity":0.5,
    "randomized_assignment":true,
    "assignment_id":"randomized-trial-001",
    "context":{"uncertainty":0.4,"harm":1.0},
    "action_result":{"alternate_prediction":1},
    "final_prediction":1,
    "ground_truth":1,
    "observed_cost":0.9,
    "latency_ms":12.0,
    "provider_version":"local-runner-v1"
  }'
```

Only submit a completed record after the outcome and retrospective label are genuinely observed and quality-checked. Do not fabricate propensity, randomization, provider, cost, or latency metadata.

For an execution already recorded as pending, use the linked completion route. It appends a new child event, preserves the original pending record, and inherits the original propensity rather than allowing the completion request to invent one. See [Milestone 66](../research/docs/milestone66-linked-outcome-completion.md).

To use transactional SQLite storage, set `VIMARSH_OUTCOME_LEDGER_BACKEND=sqlite` and configure `VIMARSH_OUTCOME_LEDGER=research/data/action_outcomes.sqlite3`. Migrate an existing JSONL history from the `research/` directory with `python -m src.verification.ledger_migration --source data/action_outcomes.jsonl --destination data/action_outcomes.sqlite3`. The migration verifies both histories, is resumable, and never deletes the source. See [Milestone 70](../research/docs/milestone70-transactional-outcome-ledger.md).

## Ledger and research limitations

- The default JSONL ledger is append-only by application convention and tamper-evident through a SHA-256 hash chain. Keep it to a single API worker.
- An optional SQLite backend provides transactional local multi-process writes, unique event IDs and parent-completion linkage, append-only triggers, and the same hash-chain verification. Select it with `VIMARSH_OUTCOME_LEDGER_BACKEND=sqlite` and point `VIMARSH_OUTCOME_LEDGER` at a `.sqlite3` file. SQLite is not a distributed database or a substitute for access-controlled backups.
- The contextual estimator's lower-bound output is a diagnostic, not a finite-sample guarantee or causal effect estimate.
- Propensity adjustment does not remove unmeasured confounding or repair incorrect logging.
- The dashboard's `/v1/actions/alternate-model/execute` route is an explicit local inference action. It runs only models already present in the trusted local bundle and returns outputs plus measured inference latency; it does not record ground truth or automatically select a final prediction. The protected `/v1/research/execute/alternate-model` route additionally appends a pending event. Submit a separate completed outcome record after a final result and ground truth are genuinely available. Reuse the returned `case_id`, baseline prediction, and `context_for_outcome_completion` values when recording that outcome. Do not invent a propensity. A deterministic/manual run without a defensible assignment propensity is not eligible for the propensity-adjusted estimator.

The allocator recommends allocations; it does not execute selected actions.
- Human review and additional evidence remain non-operational without real providers and measured outcomes.

## Operator-managed human-review queue

The local review queue is an optional, protected workflow for an actual operator to claim and adjudicate cases. It is not an automated reviewer, does not guarantee reviewer availability, and does not provide enterprise identity or role management.

Configure a separate server-side shared token and a persistent SQLite path:

```bash
export VIMARSH_REVIEWER_API_TOKEN='use-a-different-long-random-secret'
export VIMARSH_REVIEW_QUEUE_DB=research/data/review_queue.sqlite3
```

The container demo passes these settings from `.env.example` and stores the queue database in the persistent research-data volume. Never put the reviewer token in Vite variables or browser code.

- `POST /v1/reviews`: enqueue a case with a case ID, prediction, rationale, context, and priority.
- `GET /v1/reviews?status=pending&limit=50`: list queue entries.
- `POST /v1/reviews/{review_id}/claim`: atomically claim a pending case for a reviewer ID.
- `POST /v1/reviews/{review_id}/complete`: record the reviewer's note, final prediction, and optional retrospective ground truth.

Send the token in `X-Vimarsh-Reviewer-Token`. The service rejects duplicate case IDs and prevents a second reviewer from claiming an already-claimed case. A completion is accepted only from the reviewer ID that claimed the case. Reviewer IDs are operator-supplied labels; the shared token is not a substitute for individual accounts, MFA, or role-based access control. Do not expose this queue publicly. The workflow is an initial local operator integration and still requires identity, access policy, audit/retention controls, reviewer training, and independent operational validation before consequential use.


## Operator-managed review and manual evidence workflows

Two optional local workflows are available behind separate server-side tokens:

- Human review queue: set `VIMARSH_REVIEWER_API_TOKEN` and optionally `VIMARSH_REVIEW_QUEUE_DB`. The API exposes `POST/GET /v1/reviews`, `POST /v1/reviews/{review_id}/claim`, and `POST /v1/reviews/{review_id}/complete`. Cases are persisted in SQLite; claims are atomic and completion is restricted to the reviewer ID that claimed the case.
- Manual evidence intake: set `VIMARSH_EVIDENCE_API_TOKEN` and optionally `VIMARSH_EVIDENCE_DB`. The API exposes `POST /v1/evidence` and `GET /v1/evidence/{case_id}`. Each record retains a source name, source reference, submitted content, metadata, and SHA-256 content digest in an append-only SQLite register.

The dashboard provides operator forms for both workflows. Tokens remain in page memory and are not written to local storage. These are controlled local operator workflows, not third-party provider integrations: evidence is submitted by an operator and is not independently fetched or verified. Reviewer IDs are labels behind a shared token, not individual authenticated identities. Do not expose either endpoint publicly. Production use still requires an identity provider, per-user authorization, rate limiting, audit/retention policy, encrypted backups, secure secret management, and operational validation.
