# VIMARSH demonstration runbook

This is a reproducible local research demonstration using the Wine Quality benchmark and a trusted model bundle generated by the repository's training pipeline. It is not a production deployment or real-world validation.

## What to demonstrate

1. Explain the flow: base prediction -> reliability estimate -> risk = estimated error probability x harm -> hard action/budget constraints -> recommendation or abstention.
2. Show the React dashboard loading the model feature schema and live action capabilities from FastAPI.
3. Click **Load example wine sample**, set harm to 8 and remaining budget to 2, then evaluate. This makes the risk calculation and feasible alternate-model option easier to demonstrate when the estimated error probability is above the configured acceptance threshold.
4. Explain the primary prediction, confidence, estimated error probability, baseline risk, recommended action, and rationale.
5. If the capability panel confirms an alternate model is available, click **Run alternate models** to show its explicit local predictions and measured inference latency. Explain that the primary prediction is not automatically replaced.
6. Change the budget to demonstrate how feasibility constraints affect the recommendation.
7. Explain that the main decision panel still separates recommendations from execution. If demonstrating the optional operator workspace, configure the separate reviewer/evidence tokens in the API environment first. Use the decision output's **Prepare this decision for human review** control to prefill a review case with the prediction, rationale, confidence, estimated error probability, and baseline risk. Confirm and submit it, then show the case moving through pending, claimed, and completed or cancelled states. Inspect its hash-chained event history, then attach manual evidence or resolve a DOI through Crossref. Crossref lookup records bibliographic metadata only and does not verify scientific claims. Alternate-model inference still requires a separate explicit action.
8. State clearly that the serving policy is a transparent baseline. The contextual estimator and constrained allocator are offline research components, not the live serving policy.
9. Use the [research evidence summary](research-evidence-summary-2026-11-02.md) for the multi-dataset findings, including mixed and negative results.

## Fastest startup: one command

Requirements: macOS/Linux, Python 3.10 or newer, Docker Desktop with Docker Compose v2, and an internet connection for the first-time dataset download.

From the repository root:

```bash
bash scripts/vimarsh-demo.sh demo
```

The helper creates an isolated `.venv-demo`, installs the minimal training dependencies, runs the existing Wine Quality training pipeline, verifies the trusted model bundle, validates Compose, builds the API and dashboard containers, and waits for the model schema and dashboard to respond. The first run downloads the benchmark dataset if it is not already present and can take several minutes. Keep the terminal open while presenting.

Useful commands:

```bash
bash scripts/vimarsh-demo.sh prepare  # train the bundle only
bash scripts/vimarsh-demo.sh up       # start containers after bundle exists
bash scripts/vimarsh-demo.sh status
bash scripts/vimarsh-demo.sh logs
bash scripts/vimarsh-demo.sh down
```

Dashboard: http://localhost:8080  
API docs: http://localhost:8000/docs  
API health: http://localhost:8000/health

The helper uses `research/models/reliability/wine_quality_reliability_bundle.joblib` by default. Custom model directories should follow the manual container instructions in [the container demo guide](../deploy/container-demo.md).

## Manual startup without Docker

### 1. Generate the trusted model bundle

From the repository root:

```bash
cd research
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-demo.txt
python experiments/run_reliability_experiments.py
```

The data loader downloads the red and white Wine Quality files from UCI if they are not already present under `research/datasets/raw/`. The reliability experiment writes:

```text
research/models/reliability/wine_quality_reliability_bundle.joblib
```

Allow training to finish before starting the API. Keep the generated bundle local and trusted; never accept user-uploaded joblib artifacts.

### 2. Start the API

Open a second terminal from the repository root:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export VIMARSH_RELIABILITY_BUNDLE="$(cd ../research && pwd)/models/reliability/wine_quality_reliability_bundle.joblib"
uvicorn app.main:app --reload
```

The API should respond at http://localhost:8000/health. Interactive documentation is at http://localhost:8000/docs.

### 3. Start the dashboard

Open a third terminal from the repository root:

```bash
cd frontend
npm install
npm run dev
```

Open the local URL printed by Vite, normally http://localhost:5173. The default API origin is http://localhost:8000; override it with `VITE_API_BASE_URL` if required.

## Demo checks

- `GET /health` returns `status: ok`.
- `GET /v1/reliability/schema` returns fitted feature names and base-model count.
- The dashboard status changes to **MODEL CONNECTED**.
- The example sample fills the feature fields and a decision request returns prediction, confidence, estimated error probability, baseline risk, and rationale.
- With risk above the acceptance threshold, reducing the remaining budget below the alternate-model cost should cause abstention rather than an infeasible recommendation.
- The dashboard labels the recommendation as not executed.
- The alternate-model button is disabled unless live capability discovery confirms an alternate model is available.

## Troubleshooting

- **Model offline / HTTP 503:** confirm training completed and `VIMARSH_RELIABILITY_BUNDLE` points to the expected file.
- **Feature schema mismatch:** use all fields rendered by the dashboard. Do not substitute the wine-quality target label or omit `wine_type`.
- **CORS error:** use the configured local dashboard origin (`http://localhost:5173` for Vite or `http://localhost:8080` for Compose). Set `VIMARSH_CORS_ORIGINS` to the exact origin before starting the API. Wildcard origins are rejected.
- **Missing packages:** activate the virtual environment for the relevant service and install its requirements.
- **Container startup failure:** run `bash scripts/vimarsh-demo.sh logs` or `docker compose -f compose.yaml logs --tail=100`.

## Claims to make accurately

- Wine Quality, MAGIC Gamma Telescope, HTRU2, Banknote, and Ionosphere are offline tabular benchmarks, not domain deployment validation.
- The reliability estimator is trained from out-of-fold model-prediction features.
- The current serving API uses a transparent baseline policy for recommendations; it does not automatically execute verification actions.
- The action-outcome ledger, contextual benefit estimator, and constrained allocator are research-stage. Offline measured alternate-model substitution and simulated review assumptions must be described as such.
- The contextual action-benefit experiment abstained on all held-out cases in its reported run. This is a negative result and a current limitation, not evidence of superiority.
- Do not claim causal real-world risk reduction, operational human review, evidence-provider integration, production readiness, or patentability from this prototype.


## Optional operator workflows

The dashboard includes a protected local review queue and manual evidence intake panel. To enable them, copy `deploy/.env.example` to `.env`, then set distinct strong random values for `VIMARSH_REVIEWER_API_TOKEN` and `VIMARSH_EVIDENCE_API_TOKEN`. Restart Compose after changing environment values. Tokens are entered into the dashboard when an operator uses the corresponding panel and are held only in page memory.

The review queue supports enqueue, claim, and completion. Manual evidence intake stores the submitted source name, reference, text, metadata, and SHA-256 digest. It does not fetch or validate the external source. Reviewer IDs are operator-provided labels, not individual authenticated identities. Keep the services bound to loopback and do not use these local workflows for consequential decisions without a security and operational review.


## Optional operator-workflow demonstration

Set `VIMARSH_REVIEWER_API_TOKEN` and `VIMARSH_EVIDENCE_API_TOKEN` in the API environment before starting the demo. Keep both API and dashboard bound to loopback. In the operator workspace, create a sample review case, claim it using a reviewer label, and complete or cancel it. Open its history and show the audit-chain verification result. Add a short manual evidence record, or resolve a known DOI using the Crossref lookup, then inspect the stored record and digest status. Do not use real personal or confidential data. Reviewer labels are not authenticated identities, and DOI metadata retrieval is not source-claim validation.
